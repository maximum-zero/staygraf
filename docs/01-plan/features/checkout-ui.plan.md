> **Summary**: 장바구니에서 선택한 전문 자재를 모의 로그인 이후 단일 주문서에서 검토하고 카드 또는 무통장입금 주문으로 완료하는 사용자 경험

## 1. 사용자 의도

장바구니에서 배송 방식이 다른 상품 묶음을 선택한 사용자가 해당 구성을 잃지 않고 주문서로 이동해야 한다. 주문자는 상품·배송 조건·최종 금액을 한 화면에서 검토하고, 실제 PG를 연결하지 않은 상태에서도 결제수단 선택부터 처리·완료까지의 전체 구매 경험을 확인할 수 있어야 한다.

일반 사용자와 업체 구매자는 동일한 일반 회원·주문 폼을 사용한다. 주문서에서는 개인·업체 유형을 구분하거나 사업자 정보를 수집하지 않는다. 업체명과 견적 수신 정보는 후속 견적서 기능에서 별도로 다룬다.

## 2. 확정 원칙

- 주문과 견적이 사용할 상품·가격 스냅샷 구조는 함께 고려한다.
- 사용자 화면 구현은 주문 플로우를 먼저 완결하고 견적 플로우를 후속으로 연결한다.
- 한 주문은 배송지 한 곳만 사용한다.
- 실제 회원 인증과 PG 없이 모의 로그인·모의 결제로 사용자 흐름을 검증한다.
- 주문 상품은 제출 직전 현재 카탈로그 데이터로 다시 검증한다.
- 주문 생성 이후에는 생성 시점의 상품·옵션·가격·세금·배송 조건을 스냅샷으로 보존한다.

## 3. 검토한 대안

### 3.1 단일 주문서와 우측 결제 요약

- 구조: 주문 상품, 주문자·배송지, 결제수단과 동의를 한 화면에 배치하고 데스크톱 우측에 결제 요약을 고정한다.
- 장점: 국내 이커머스 사용자에게 익숙하고 입력 내용과 최종 금액을 동시에 검토할 수 있다.
- 단점: 모바일 세로 길이가 길어진다.
- 공수: 중간
- 결정: 채택한다.

### 3.2 단계형 주문서

- 구조: 배송 정보, 결제수단, 최종 확인을 별도 단계로 분리한다.
- 장점: 한 번에 입력할 정보가 적어 보인다.
- 단점: 이전 정보의 비교·수정이 번거롭고 현재 필드 규모에 비해 이동이 많다.
- 공수: 높음
- 결정: 제외한다.

### 3.3 아코디언 주문서

- 구조: 상품·배송지·결제수단 영역을 접고 펼친다.
- 장점: 화면이 짧고 모바일에서 단정해 보인다.
- 단점: 입력 오류와 주문 검토 정보가 숨겨질 수 있다.
- 공수: 중간 이상
- 결정: 제외한다.

## 4. YAGNI 검토

### Must Have

- 장바구니 선택 묶음만 주문서로 전달
- 모의 로그인과 주문서 복귀
- 주문자·수령 정보와 배송 요청사항
- 배송 방식별 상품 묶음과 배송비 확인
- 카드·무통장입금 선택
- 상품 금액·선불 배송비·착불 안내·최종 금액
- 결제 전 상품 조건 재검증
- 중복 제출 방지와 처리 피드백
- 주문번호와 주문 완료 화면
- 주문한 묶음만 장바구니에서 제거
- 주문 초안·완료 주문의 브라우저 보관과 만료

### Nice to Have

- 주문 상품 영역 접기·펼치기
- 배송 요청사항의 직접 입력
- 무통장입금 완료 화면의 입금 기한·샘플 계좌 안내

배송 요청사항 직접 입력과 입금 기한·계좌 안내는 구매 완료에 필요한 정보이므로 최종 Must Have로 승격한다.

### Won't Do

- 실제 인증·회원 서버
- 실제 PG·카드번호 입력
- 쿠폰·포인트·프로모션
- 간편결제·가상계좌·실시간 계좌이체
- 현금영수증·세금계산서
- 묶음별 서로 다른 배송지
- 배송 희망일 지정
- 주문 취소·교환·환불
- 주문 목록·상세와 마이페이지
- 견적 정보 입력·발행

배송지 주소록과 공식 주소 검색은 후속 승인된 [배송지 관리 UI 계획](./shipping-address-ui.plan.md)에서 별도 구현한다.

## 5. 화면 범위

| 화면 | 경로 | 역할 |
|---|---|---|
| 모의 로그인 | `/login?returnTo=/checkout` | 주문 진입 인증과 내부 경로 복귀 |
| 주문·결제 | `/checkout` | 상품·배송·결제수단·금액 확인과 주문 생성 |
| 주문 완료 | `/orders/[orderId]/complete` | 주문번호와 결제 결과·배송 묶음 확인 |

사용자 여정은 다음과 같다.

`장바구니 → 모의 로그인 → 주문·결제 → 모의 처리 → 주문 완료`

이미 로그인한 사용자는 로그인 화면을 건너뛴다. 선택 상품이 없거나 모두 구매 불가하면 주문서 진입을 막고 장바구니로 복귀시킨다.

## 6. 기능 요구사항

### 6.1 모의 로그인

- 이메일과 비밀번호 형식의 로그인 폼을 제공한다.
- 화면 검증을 위한 데모 계정 자동 입력 기능을 제공한다.
- 로그인 상태는 현재 탭 세션 동안만 유지한다.
- 로그인 성공 후 검증된 내부 `returnTo` 경로로 복귀한다.
- 실제 비밀번호·토큰을 서버로 전송하거나 저장하지 않는다.

### 6.2 주문자 정보

- 이름, 휴대전화, 이메일을 입력한다.
- 각 필드는 명시적 라벨을 사용한다.
- 휴대전화와 이메일은 형식 오류를 필드 가까이에 표시한다.

### 6.3 배송 정보

- 수령인, 연락처, 우편번호, 주소, 상세주소를 입력한다.
- `주문자 정보와 동일`을 선택하면 이름과 연락처를 동기화한다.
- 배송 요청사항은 다음 값을 제공한다.
  - 배송 전 연락 바랍니다.
  - 현장 담당자에게 연락 바랍니다.
  - 직접 입력
- 화물 택배 배송 또는 개별 화물 운송 상품이 하나라도 있으면 주소를 필수로 요구한다.
- 직접 수령 상품만 포함하면 주소 필드를 숨기고 방문자명·연락처만 사용한다.
- 직접 수령이 배송 상품과 함께 포함된 경우 동일한 주문자·수령 연락처를 사용한다.

### 6.4 주문 상품과 배송 묶음

- 장바구니에서 선택한 묶음만 표시한다.
- 본품명, 옵션, 규격, 수량, 주문 단위, 추가 상품과 가격을 표시한다.
- 배송 방식별 묶음과 선불·착불·0원 조건을 구분한다.
- 주문서에서는 수량·옵션·추가 상품·배송 방법을 변경하지 않는다.
- 구성 변경이 필요하면 장바구니로 돌아가는 경로를 제공한다.
- 같은 배송 방식으로 표시되어도 합배송을 보장하지 않는다고 안내한다.

### 6.5 금액과 재검증

- 상품 금액, 선불 배송비와 최종 결제 금액을 구분한다.
- 개별 화물 운송비는 합계에서 제외하고 `착불 운송비 별도`로 표시한다.
- 제출 직전에 상품, 옵션, 규격, 추가 상품, 가격과 배송 가능 여부를 다시 검증한다.
- 조건이 변경되면 주문 생성을 중단하고 변경 내용을 확인할 수 있도록 장바구니 복귀를 안내한다.

### 6.6 결제수단

- `신용·체크카드`와 `무통장입금`을 제공한다.
- 카드번호나 실제 결제정보를 입력받지 않는다.
- 무통장입금은 입금자명을 필수로 받는다.
- 주문 내용과 결제 조건 확인 동의를 필수로 받는다.
- 처리 중에는 제출 버튼을 비활성화하고 진행 상태를 알린다.
- 동일 주문서에서 중복 주문이 생성되지 않게 한다.

### 6.7 주문 생성과 완료

- 카드 주문은 `결제 완료` 상태로 생성한다.
- 무통장입금 주문은 `입금 대기` 상태로 생성한다.
- 주문번호와 생성 일시를 기록한다.
- 상품명, 옵션, 규격, 수량, 주문 단위, 단가, 공급가액, 부가세, 추가 상품, 배송 방식과 배송비를 스냅샷으로 보존한다.
- 주문 생성 성공 후 주문 대상 묶음만 장바구니에서 제거한다.
- 선택하지 않은 장바구니 묶음은 유지한다.
- 주문 초안을 제거하고 완료 화면으로 이동한다.
- 완료 화면은 새로고침 후에도 동일한 주문을 표시한다.
- 무통장입금 완료 화면은 입금 기한과 샘플 계좌를 표시한다.
- 장바구니와 상품 탐색으로 돌아가는 경로를 제공한다.

## 7. UI·반응형 요구사항

### 7.1 공통

- 기존 Pretendard, 브랜드 그린, 중립 배경, 선과 4px radius 체계를 유지한다.
- 과장된 에디토리얼 타이포·새 팔레트·장식적 배지를 추가하지 않는다.
- 일반 커머스 헤더 대신 `STAYGRAF`, `주문·결제`, `장바구니로 돌아가기`만 있는 주문 전용 헤더를 사용한다.
- 입력 오류는 각 필드 아래에 표시하고 제출 시 첫 오류로 포커스를 이동한다.
- 모든 핵심 조작 영역은 최소 44×44px이다.

### 7.2 데스크톱

- 본문과 344px 결제 요약을 나란히 배치한다.
- 결제 요약은 header 아래에서 sticky로 동작한다.
- 상품·배송·결제 정보와 최종 금액의 정렬축을 일관되게 유지한다.

### 7.3 태블릿

- 결제 요약을 본문 아래의 전체 폭 카드로 이동한다.
- 모바일 고정 결제 바는 사용하지 않는다.

### 7.4 모바일

- 모든 섹션을 한 열로 표시한다.
- 하단에 최종 금액과 결제 행동을 고정한다.
- safe area와 고정 영역 높이만큼 본문 하단 여백을 확보한다.
- 전화번호·이메일·우편번호에 적절한 `inputMode`를 제공한다.

## 8. 상태와 보관 정책

| 상태 | 저장 위치 | 만료 | 책임 |
|---|---|---:|---|
| 장바구니 | 기존 Zustand localStorage persist | 30일 | 상품 묶음과 선택 상태 |
| 모의 로그인 | sessionStorage | 탭 종료 | 모의 회원과 로그인 여부 |
| 주문 초안 | localStorage | 24시간 | 대상 묶음 ID와 작성 중인 폼 |
| 모의 주문 | localStorage | 7일 | 생성 시점 주문 스냅샷 |

- 저장소마다 version을 두고 유효하지 않은 데이터는 안전하게 초기화한다.
- 카드번호·계좌 비밀번호 등 실제 결제정보는 어떤 저장소에도 기록하지 않는다.
- 주문 초안에는 현재 장바구니 묶음 ID를 저장하고 판매가격 원본으로 사용하지 않는다.
- 완료 주문만 생성 시점 가격과 배송 정보를 보존한다.

## 9. 아키텍처 고려사항

- Next.js App Router와 TypeScript strict를 유지한다.
- 폼은 이미 설치된 React Hook Form과 Zod를 사용한다.
- 브라우저 상태는 Zustand persist를 사용하되 세션·초안·주문 저장 책임을 분리한다.
- 현재 상품 재검증은 기존 카탈로그·장바구니 resolve 로직을 확장한다.
- 주문 생성은 다음 순서를 하나의 도메인 동작으로 처리한다.
  1. 선택 묶음 확인
  2. 현재 상품 조건 재검증
  3. 금액 계산
  4. 주문번호와 스냅샷 생성
  5. 주문 저장
  6. 주문 대상 장바구니 제거
  7. 주문 초안 제거
  8. 완료 화면 이동
- 실제 백엔드 연결 시 주문 생성 API 한 건으로 대체할 수 있도록 UI와 생성 로직을 분리한다.

- [ ] 비회원은 모의 로그인 후 동일한 주문서로 복귀한다.
- [ ] 새로고침·뒤로가기 후에도 선택 상품과 주문 초안이 유지된다.
- [ ] 필수 입력과 전화번호·이메일·우편번호 오류가 각 필드 아래 표시된다.
- [ ] 직접 수령 상품만 있으면 배송 주소를 요구하지 않는다.
- [ ] 배송 상품이 포함되면 배송 주소를 필수로 요구한다.
- [ ] 선불 배송비만 합계에 포함되고 착불은 별도로 표시된다.
- [ ] 결제 직전에 최신 가격·판매·배송 조건을 재검증한다.
- [ ] 처리 중 중복 주문이 생성되지 않는다.
- [ ] 카드 주문은 `결제 완료`, 무통장입금은 `입금 대기`로 생성된다.
- [ ] 주문 성공 후 주문한 묶음만 장바구니에서 제거된다.
- [ ] 주문 완료 화면을 새로고침해도 동일 주문이 표시된다.
- [ ] 키보드만으로 로그인부터 주문 완료까지 진행할 수 있다.
- [ ] 320·390·768·1024·1440px에서 가로 깨짐과 콘텐츠 가림이 없다.
- [ ] typecheck, lint, unit test, E2E와 production build가 통과한다.
- [ ] 기획·디자인·접근성 최종 검수에서 P0가 없다.

## 12. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 브라우저 저장소에 개인정보 잔존 | 높음 | 초안 24시간·주문 7일 만료, 실제 결제정보 저장 금지 |
| 모의 로그인을 실제 인증으로 오해 | 중간 | 데모 계정과 화면 검증용 인증 안내 |
| 주문 직전 가격·배송 변경 | 높음 | 제출 직전 현재 상품 데이터 재검증 |
| 결제 버튼 연속 클릭 | 높음 | 첫 제출 즉시 잠금과 중복 생성 방지 |
| 뒤로가기 후 재결제 | 높음 | 생성된 주문 ID가 있으면 기존 완료 화면 복원 |
| 배송 그룹을 합배송으로 오해 | 중간 | 그룹 설명과 상품별 배송비 표시 유지 |
| 착불 금액을 결제액으로 오해 | 높음 | 최종 금액 인접 위치에 착불 별도 안내 |
| 모바일 고정 바가 입력을 가림 | 중간 | safe area와 본문 하단 여백 동시 적용 |
| 외부 `returnTo` 악용 | 높음 | 서비스 내부 경로만 허용 |
| 저장 구조 변경 | 중간 | persist version과 만료·초기화 처리 |

## 13. 검증 계획

### 단위 테스트

- 세션·초안·주문 만료
- 전화번호·이메일·우편번호와 조건부 배송지 검증
- 선불·착불·직접 수령 금액 계산
- 카드·무통장 주문 상태
- 주문 스냅샷과 주문번호 생성
- 주문 대상 장바구니 제거
- 내부 복귀 경로 검증

### E2E

- 비회원 장바구니 → 로그인 → 주문서 복귀
- 카드 모의 결제 → 결제 완료
- 무통장입금 → 입금 대기와 계좌 안내
- 필드 오류와 첫 오류 포커스
- 가격·배송 조건 변경 시 주문 차단
- 주문 완료 새로고침
- 미선택 장바구니 묶음 유지
- 주요 반응형 너비와 키보드 주문 여정
