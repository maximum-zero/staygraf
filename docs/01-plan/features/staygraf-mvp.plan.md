> Version: 1.0.0 | Date: 2026-08-07 | Status: Approved

## 1. Overview

### 1.1 Purpose

STAYGRAF는 인테리어 업체가 복잡한 자재 규격과 구매 조건을 명확하게 확인하고 구매할 수 있도록 돕는 전문 인테리어 자재 커머스다.

완성된 공간 콘텐츠를 `GRAF`라는 고유 단위로 제공하고, GRAF에 사용된 상품과 시공업체를 연결한다. 인테리어 업체는 다른 업체의 결과물과 자재 활용 방식을 참고할 수 있고, 일반 사용자는 완성된 공간을 통해 상품을 더 구체적으로 이해할 수 있다.

### 1.2 Background

인테리어 자재는 일반 소비재와 달리 카테고리와 상품에 따라 표시 가격, 실제 구매 단위, 포장 규격, 부가세 표기, 배송 방식이 크게 달라진다. 타일처럼 면적으로 비교하지만 박스나 장으로 구매하는 상품이 있는 반면, 수전과 조명은 옵션별 이미지·규격·가격이 구매 판단에 더 큰 영향을 준다.

초기 제품은 모든 업계 규칙을 범용화하지 않는다. 판매 방식이 다른 대표 카테고리 세 개를 고정하고, GRAF 탐색부터 상품 검토, 장바구니, 견적서, 주문 또는 가격 문의까지 하나의 완결된 경험으로 구현한다.

### 1.3 Core Users

- 주요 구매자: 인테리어 업체
- 함께 이용할 사용자: 홈 인테리어에 관심 있는 일반 사용자
- 운영 사용자: 상품·업체·GRAF·문의·주문을 관리하는 관리자

초기에는 업체 회원과 일반 회원을 구분하지 않는다. 두 사용자 모두 동일한 상품과 가격을 확인하며, 활용 목적과 정보 해석 방식이 다르다. 관리자 계정은 일반 회원과 완전히 분리한다.

### 1.4 Product Principle

> 서로 다른 자재의 실제 거래 조건을 숨기지 않되, 업체와 일반 사용자 모두가 이해하고 행동할 수 있는 구조로 제공한다.

## 2. Goals

### 2.1 Primary Goals

- [ ] 타일·빅슬랩, 수전, 조명 세 카테고리에서 서로 다른 상품 규칙을 정확하게 표현한다.
- [ ] GRAF에서 공간, 시공업체, 사용 상품을 함께 발견할 수 있게 한다.
- [ ] 옵션별 이미지·규격·가격 차이를 목록과 상세에서 일관되게 전달한다.
- [ ] 사용자가 상품별 배송 방식을 선택하고 여러 배송 묶음을 한 번에 주문할 수 있게 한다.
- [ ] 업체 구매에 필요한 구매 전 견적서를 생성·보관·재출력할 수 있게 한다.
- [ ] 즉시 구매 상품과 가격 문의 상품을 명확하게 분리한다.
- [ ] 실제 결제 모듈을 제외한 주문·결제 사용자 경험을 완성한다.
- [ ] 사용자 화면을 실제 브라우저에서 먼저 검증한 뒤 ERD·API·백엔드를 설계한다.

### 2.2 Alternatives Explored

#### A. 업체 구매 기능 우선

- 장점: 전문 자재 거래 규칙에 집중할 수 있다.
- 단점: GRAF와 브랜드 고유 경험이 늦게 드러난다.

#### B. GRAF와 업체 연결 우선

- 장점: 공간 중심 경험과 시각적 정체성을 빠르게 보여줄 수 있다.
- 단점: 실제 주요 사용자인 업체의 자재 구매 가치가 약해진다.

#### C. 대표 카테고리 수직 완성 — 선택

- 타일·빅슬랩, 수전, 조명에서 GRAF부터 구매 또는 가격 문의까지 전체 흐름을 구현한다.
- 제한된 범위에서 콘텐츠와 전문 커머스를 함께 검증할 수 있다.
- 실제 차이를 확인한 후에만 공통 규칙을 추출할 수 있다.
- 관리자용 범용 규칙 편집기를 조기에 만드는 일을 피할 수 있다.

### 2.3 Non-Goals

- 실제 PG 연동
- 업체별 차등 가격 또는 회원 등급별 가격
- 업체와 고객의 내부 메시지, 공사 계약, 진행 상태 관리
- 업체의 직접 GRAF 등록
- 가격 문의 답변의 주문 전환
- 주문제작
- 정확한 재고 수량 및 옵션별 재고 차감
- 자유로운 카테고리 생성과 범용 규칙 빌더
- 모든 인테리어 자재 카테고리 지원
- 복잡한 교환·반품 자동화
- 도면 기반 자재 배치와 견적 계산
- AI 추천

## 3. Scope

### 3.1 Initial Categories

#### 타일·빅슬랩

- 면적 기준 정보와 박스·장 구매 단위
- 포장당 수량과 시공 가능 면적
- 규격·색상·마감 옵션
- 고정 가격 또는 가격 문의
- 화물 배송과 직접 수령 등 상품별 배송 방식

#### 수전

- 개·세트 구매 단위
- 용도와 제한된 하위 분류
- 색상·마감·규격 옵션
- 옵션별 이미지와 가격
- 상품별 배송 방식

#### 조명

- 개·세트 구매 단위
- 제한된 하위 분류
- 색상·크기 등 상품에 필요한 옵션
- 옵션별 이미지와 가격
- 상품별 배송 방식

다음 카테고리 확장 후보는 바닥재, 위생도기, 시계다. 초기 세 카테고리의 구조를 검증한 뒤 별도 범위로 다룬다.

### 3.2 GRAF

- 사용자는 GRAF 목록과 상세를 탐색할 수 있다.
- GRAF는 여러 이미지와 기본 공간 정보를 가질 수 있다.
- 사용자는 GRAF를 제작한 업체를 확인할 수 있다.
- 사용자는 GRAF에 연결된 상품을 확인하고 상품 상세로 이동할 수 있다.
- 사용자는 같은 업체의 다른 GRAF를 탐색할 수 있다.
- GRAF와 상품을 연결하는 구체적인 인터랙션은 디자인 단계에서 대안을 비교하고 승인한다.

### 3.3 Contractor

- 업체는 독립된 데이터로 관리한다.
- 관리자는 업체를 등록·수정·비활성화할 수 있다.
- 업체는 업체명, 소개, 전문 분야, 활동 지역, 로고·대표 이미지와 공개 연락 채널을 가질 수 있다.
- 하나의 업체에 여러 GRAF를 연결할 수 있다.
- 사용자 화면에는 업체 프로필과 연결된 GRAF를 노출한다.
- 서비스 내부 문의, 메시지, 계약 및 공사 진행 관리는 제공하지 않는다.

### 3.4 Product Catalog

- 사용자는 초기 세 카테고리와 제한된 하위 분류에서 상품을 탐색할 수 있다.
- 카테고리별 필터와 정렬을 제공한다.
- 공통 필터, 카테고리 전용 필터, 옵션 기반 필터를 구분한다.
- 구체적인 필터 항목은 실제 상품 샘플을 분석한 뒤 사용자 화면 설계 전에 확정한다.
- 옵션 기반 필터 결과와 목록 이미지가 서로 모순되지 않아야 한다.
- 필터 상태는 뒤로 가기와 공유 흐름을 고려한다.

### 3.5 Product and Option Boundary

#### 상품이 담당하는 정보

- 카테고리와 하위 분류
- 가격 방식
- 가능한 배송 방식
- 판매 상태
- 상품 공통 설명
- 공통 구매·배송 안내

#### 옵션이 담당하는 정보

- 색상·마감·규격 등 선택값
- 옵션별 가격
- 옵션별 대표 이미지와 상세 이미지
- 옵션 선택에 따라 달라지는 포장당 수량과 시공 가능 면적

옵션별 배송 예외와 옵션별 가격 문의 예외는 허용하지 않는다. 가격 방식이나 배송 조건이 다르면 별도 상품으로 등록한다.

### 3.6 Product Media

- 상품은 기본 대표 이미지를 가질 수 있다.
- 옵션은 대표 이미지와 여러 상세 이미지를 가질 수 있다.
- 목록에서 옵션 대표 이미지를 확인하고 선택할 수 있는 경험을 검토한다.
- 상세에서 옵션 선택 시 이미지·가격·규격 정보가 함께 일관되게 변경되어야 한다.
- 목록과 상세의 최종 인터랙션은 디자인 검토 후 확정한다.

### 3.7 Pricing

상품 가격 방식은 상품 단위로 다음 중 하나를 사용한다.

#### 구매 가능

- 옵션별 가격을 설정할 수 있다.
- 목록과 상세에서 가격 또는 시작 가격을 확인할 수 있다.
- 사용자는 장바구니와 바로 구매 흐름을 이용할 수 있다.

#### 가격 문의

- 모든 옵션이 가격 문의 대상이다.
- 목록과 상세에서 가격 대신 가격 문의 상태를 표시한다.
- 구매 행동 대신 가격 문의 행동을 제공한다.
- 일반 장바구니에는 담지 않는다.

모든 공개 가격은 부가세 포함 또는 별도 여부를 명확하게 표시한다.

### 3.8 Price Inquiry

- 로그인 회원만 가격 문의를 접수할 수 있다.
- 문의에는 상품, 옵션, 예상 수량, 이름, 연락처와 요청 내용을 포함한다.
- 필요 시 현장 또는 배송 지역 정보를 입력할 수 있다.
- 관리자는 문의를 조회하고 가격과 안내 내용을 답변할 수 있다.
- 문의 상태는 `접수`, `답변 완료`, `종료`로 관리한다.
- 가격 문의 답변을 장바구니나 주문으로 자동 전환하지 않는다.

### 3.9 Sales Status

- 정확한 재고 수량은 관리하지 않는다.
- 상품은 `판매 중`, `품절`, `판매 중지` 상태를 가진다.
- 품절 상품은 정보와 GRAF 연결을 유지하되 구매할 수 없다.
- 판매 중지 상품의 공개 여부는 관리자가 제어한다.
- 가격 문의 여부와 판매 상태는 서로 다른 개념으로 관리한다.

### 3.10 Area-to-Quantity Calculator

- 타일·빅슬랩 상품에서 필요한 면적을 입력할 수 있다.
- 옵션의 포장당 시공 가능 면적을 기준으로 이론상 최소 구매 수량을 계산한다.
- 구매 단위보다 작은 결과는 부족하지 않도록 올림 처리한다.
- 계산 결과에는 최소 구매 수량과 실제 구매 면적을 표시한다.
- 로스율을 계산하거나 관리하지 않는다.
- 재단과 파손으로 추가 수량이 필요할 수 있다는 일반 안내를 제공한다.
- 사용자는 계산 결과를 구매 수량 입력에 적용할 수 있다.
- 적용 후 수량을 확인·수정하고 별도 행동으로 장바구니에 담는다.
- 계산은 프론트에서 처리하되 포장당 수량과 시공 면적은 상품 데이터로 제공한다.

### 3.11 Delivery

- 배송 방식은 상품 단위로만 설정한다.
- 하나의 상품은 여러 가능한 배송 방식을 가질 수 있다.
- 옵션과 카테고리에는 배송 예외를 두지 않는다.
- 사용자는 장바구니의 각 상품에서 가능한 배송 방식 중 하나를 선택한다.
- 장바구니는 현재 선택한 배송 방식별로 상품을 나눠 표시한다.
- 동일한 배송 방식 그룹이 실제 합배송을 보장하지는 않는다.
- 상품별 배송비, 선불·착불, 확정 금액·별도 안내 상태를 표현할 수 있어야 한다.

### 3.12 Cart, Order, and Mock Payment

- 비회원도 장바구니를 사용할 수 있다.
- 사용자는 배송 그룹을 넘나들며 주문할 상품을 선택할 수 있다.
- 선택한 모든 상품은 한 번에 주문·결제한다.
- 주문은 한 건으로 생성하되 내부에 여러 배송 묶음을 가질 수 있다.
- 배송 묶음별 상태와 운송장 정보를 관리할 수 있다.
- 선택하지 않은 상품은 장바구니에 유지한다.
- 주문 시 로그인을 요구한다.
- 실제 PG 대신 결제수단 선택, 처리, 완료까지의 모의 결제 흐름을 제공한다.
- 실제 카드·계좌 정보를 입력받거나 저장하지 않는다.

### 3.13 Pre-Purchase Quotation

- 로그인 회원은 장바구니에서 선택한 구매 가능 상품으로 견적서를 생성할 수 있다.
- 가격 문의, 품절, 판매 중지 상품은 자동 견적서 대상에서 제외한다.
- 견적서에는 견적번호, 생성일, 수신 정보, 상품, 옵션, 수량, 구매 단위, 배송 방식, 공급가액, 부가세, 배송비와 총액을 포함한다.
- 견적 수신 정보는 생성 시 입력하며 업체명 또는 개인 이름을 사용할 수 있다.
- 견적 생성 시점의 상품명·옵션·가격·세금·배송 정보를 스냅샷으로 보존한다.
- 견적서는 주문이나 재고 확보를 의미하지 않는다.
- 인쇄용 화면을 제공하고 사용자가 브라우저 기능으로 인쇄하거나 PDF로 저장할 수 있게 한다.
- 마이페이지에서 견적서 이력을 조회하고 재출력할 수 있다.
- 견적서에서 주문으로 자동 전환하지 않는다.

### 3.14 Authentication Boundary

- GRAF, 업체, 상품, 옵션과 면적 계산은 비회원에게 공개한다.
- 장바구니는 비회원에게 허용한다.
- 비회원 장바구니는 로그인 후 회원 장바구니로 이전한다.
- 주문, 가격 문의, 견적서 생성과 개인 이력 조회는 로그인을 요구한다.
- 구매자는 하나의 일반 회원 체계를 사용한다.
- 관리자 인증과 관리자 데이터는 일반 회원과 별도 체계로 관리한다.
- 향후 업체 계정이 필요해지면 별도 승인된 전환·연결 정책으로 확장한다.

### 3.15 Admin

- 초기 세 카테고리의 고정된 상품 등록 흐름을 제공한다.
- 관리자는 상품 공통 정보와 카테고리별 정보를 등록·수정한다.
- 관리자는 옵션별 이미지·규격·가격과 포장 정보를 관리한다.
- 관리자는 상품별 가격 방식, 배송 방식과 판매 상태를 관리한다.
- 관리자는 업체와 GRAF를 등록·수정하고 공개 상태를 제어한다.
- 관리자는 업체·GRAF·상품 관계를 관리한다.
- 관리자는 가격 문의를 조회·답변·종료한다.
- 관리자는 주문, 모의 결제 결과와 배송 묶음을 확인·관리한다.
- 범용 카테고리 규칙 편집기는 제공하지 않는다.

## 4. Non-Functional Requirements

### 4.1 Accuracy

- 상품 가격, 옵션 가격, 세금, 포장 단위와 배송 조건을 주문 전에 명확하게 보여준다.
- 견적서와 주문은 생성 시점의 가격 정보를 보존한다.
- 면적 계산 결과가 이론상 최소 수량임을 명시한다.
- 배송 방식 그룹과 실제 합배송을 구분한다.

### 4.2 Usability

- 전문 업체가 필요한 규격과 구매 조건을 빠르게 확인할 수 있어야 한다.
- 일반 사용자도 전문 용어를 이해할 수 있도록 맥락과 환산 정보를 제공한다.
- 옵션 변경 시 이미지·가격·규격이 서로 불일치하지 않아야 한다.
- 구매 가능 상품과 가격 문의 상품의 행동을 명확하게 구분한다.
- 장바구니는 배송 방식별로 구분하되 선택 상품의 결제는 한 번에 완료한다.

### 4.3 Accessibility

- 주요 탐색·옵션·장바구니·주문 기능을 키보드로 사용할 수 있어야 한다.
- 의미 있는 이미지에 대체 텍스트를 제공한다.
- 색상만으로 옵션이나 상태를 구분하지 않는다.
- 일반 텍스트와 인터랙션 요소는 적절한 대비를 유지한다.
- 모바일 인터랙션 요소는 충분한 터치 영역과 간격을 확보한다.
- 동작과 상태 변화는 보조 기술이 이해할 수 있어야 한다.

### 4.4 Performance

- GRAF와 옵션별 이미지가 초기 화면을 불필요하게 차단하지 않아야 한다.
- 화면 크기에 적합한 이미지와 최신 웹 이미지 형식을 사용한다.
- 화면 밖 이미지는 지연 로딩한다.
- 이미지 로딩 중 레이아웃 이동을 최소화한다.
- 목록과 상세에서 필요한 이미지 품질을 구분한다.

### 4.5 Security and Privacy

- 일반 회원과 관리자 인증을 분리한다.
- 관리자 기능은 관리자 인증 없이 접근할 수 없다.
- 모의 결제에서 실제 결제 정보를 수집하지 않는다.
- 가격 문의와 견적서의 개인정보는 본인과 관리자만 조회할 수 있다.
- 비밀값과 환경별 설정은 저장소에 커밋하지 않는다.

### 4.6 Maintainability and Expansion

- 초기 세 카테고리의 실제 차이를 먼저 구현한다.
- 확인되지 않은 범용 규칙과 미래 정책을 선구현하지 않는다.
- 상품 공통 정보와 카테고리·옵션별 정보를 명확하게 구분한다.
- 새 카테고리는 실제 요구를 분석한 뒤 추가한다.
- 반복되는 규칙이 확인된 이후에만 공통화한다.

### 5.2 Calculator

- [ ] 필요한 면적을 이론상 최소 구매 수량으로 계산할 수 있다.

### 5.3 Delivery and Order

- [ ] 주요 디자인 결정과 사용자 흐름에 승인 근거가 남아 있다.

## 6. Delivery Strategy and Quality Gates

### 6.1 Approved Sequence

1. 계획 문서 확정
2. 핵심 사용자 여정 정의
3. 사용자 화면 목록 확정
4. 실제 상품 샘플과 필터 속성 분석
5. 프론트 기술 스택 대안 비교 및 승인
6. Git 저장소와 문서 구조 설정
7. `AGENTS.md` 개편
8. 코딩 컨벤션과 품질 도구 설정
9. 프로젝트 기본 골격 생성
10. lint·typecheck·test·build 검증
11. UI UX Pro Max 기반 디자인 방향 비교
12. 핵심 화면을 실제 프론트로 구현
13. 브라우저에서 검토·수정·승인
14. 나머지 사용자 화면 확장
15. 화면 기반 데이터 요구사항 도출
16. ERD·API·백엔드 기술 스택 결정
17. 관리자 및 실제 기능 개발
18. 통합 검증

### 6.2 Frontend-First UI Validation

- 정적인 화면만으로 주요 UX를 승인하지 않는다.
- 백엔드와 데이터베이스 없이 로컬 샘플 데이터로 실제 브라우저 UI를 구현한다.
- 옵션 변경, 필터, 계산기, 장바구니 그룹 등 핵심 상태 변화를 동작시킨다.
- 모바일과 데스크톱에서 직접 확인한다.
- 승인된 프론트 코드를 이후 실제 데이터와 연결한다.
- 프론트 기술 스택은 구현 전에 별도 대안 검토와 승인을 거친다.
- 백엔드·데이터베이스·인프라 스택은 UI 검증 뒤 결정한다.

### 6.3 Repository and AI Guardrail Gate

프론트 UI 구현 전에 다음 항목을 제안·검토·승인하고 저장소에 반영한다.

- 프론트 프레임워크·언어·런타임·패키지 매니저 결정 기록
- 스타일링·아이콘·상태·폼·검증·테스트·이미지 처리 기준
- Git 저장소, `.gitignore`, 문서 구조
- 프로젝트 전용 `AGENTS.md`
- 코딩·파일·컴포넌트·커밋 컨벤션
- TypeScript strict, lint, format, typecheck, test, build 설정
- 환경 변수 예제와 비밀값 제외 정책
- 기능 중심 디렉터리 구조
- 샘플 데이터와 UI 코드의 분리
- 공용 컴포넌트 승격 기준
- 승인되지 않은 의존성 추가 금지
- 로딩·빈 상태·오류 상태와 접근성·반응형 기준
- 최소 CI 검사

Husky, commitlint 등 부가 도구는 자동으로 도입하지 않고 필요성과 비용을 검토한다.

### 6.4 Collaboration Gate

각 화면과 주요 기술 결정을 다음 관점으로 나눠 검토한다.

- 기획자: 화면 목적과 필수 정보
- UX 디자이너: 사용자 흐름과 상태
- UI 디자이너: 시각적 대안과 일관성
- 개발자: 구현 난이도와 재사용성
- 사용자: 최종 선택과 승인

사용자의 명시적인 승인 전에 코드나 설정을 변경하지 않는다.

### 6.5 Documentation Policy

- 제품 가치, 범위, 결정 근거와 검증 방법을 저장소 문서로 관리한다.
- `AGENTS.md`에는 실행에 필요한 규칙만 두고 계획 문서를 복제하지 않는다.
- 기술 선택은 대안과 선택 이유를 결정 기록으로 남긴다.
- UI 결정은 검토한 대안과 승인 결과를 남긴다.
- 결정되지 않은 내용을 확정 요구사항처럼 작성하지 않는다.
- 비밀값, 개인용 로컬 설정, 임시 생성물과 도구 캐시는 커밋하지 않는다.

## 7. Architecture Considerations

이 섹션은 ERD나 기술 스택을 확정하지 않는다. 사용자 화면을 검증한 뒤 상세 설계할 때 지켜야 할 책임 경계만 정의한다.

### 7.1 Conceptual Domains

- 일반 회원
- 관리자 인증
- 업체
- GRAF
- 상품·카테고리
- 옵션·미디어
- 장바구니
- 배송 방식·배송 묶음
- 주문·모의 결제
- 가격 문의
- 구매 전 견적서

### 7.2 Price Snapshot

- 장바구니는 현재 상품 정보를 참조한다.
- 견적서는 생성 시점의 상품·옵션·가격·세금·배송 정보를 보존한다.
- 주문은 주문 확정 시점의 상품·옵션·가격·세금·배송 정보를 보존한다.
- 상품 정보가 변경돼도 과거 견적서와 주문은 변경되지 않는다.

### 7.3 Guest Cart

- 비회원 장바구니는 브라우저에 임시 저장한다.
- 로그인 후 회원 장바구니로 이전한다.
- 구체적인 병합 충돌 정책은 사용자 화면 설계에서 확정한다.

### 7.4 Design Before Data Modeling

- GRAF와 상품의 연결 구조는 승인된 UI가 요구하는 데이터만 모델링한다.
- 화면에서 필요한 상품·옵션·필터 정보를 확인한 뒤 ERD를 설계한다.
- 실제 사용자 행동과 무관한 범용 구조를 조기에 만들지 않는다.
